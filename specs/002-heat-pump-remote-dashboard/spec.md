# 功能規格：熱泵遠端監控儀表板

**功能分支**: `002-heat-pump-remote-dashboard`  
**建立日期**: 2026年2月19日  
**狀態**: 草稿  
**輸入**: 使用者描述：「打造一個數位遠端管理中心，讓管理人員不需要親自跑到機房，只要打開網頁就能即時掌握所有熱泵設備的健康狀況與運作效率，並能遠端下達控制指令」

## 釐清事項

### Session 2026-02-19

- Q: 管理人員需要登入才能存取儀表板嗎？ → A: 需要登入，但採用簡化的帳號密碼驗證（企業內部使用）
- Q: 當管理人員不在觀看儀表板時，系統應該如何處理異常事件？ → A: 在儀表板內顯示通知訊息，需登入後查看（類似訊息中心）
- Q: 系統應該根據什麼標準判定設備異常並觸發紅燈/通知？ → A: 設定固定的安全閾值範圍（例如排氣溫度>85°C、壓力>3.5MPa）
- Q: 系統應該保存多長時間的歷史資料？ → A: 保存30天詳細資料，超過後自動刪除
- Q: 當管理人員 A 正在調整設備參數時，管理人員 B 應該能立即覆蓋操作嗎？ → A: 任何已登入的管理人員都能控制，但顯示最近操作記錄（操作者、時間）
- Q: 後端系統如何連接到實體熱泵設備並獲取即時資料與執行控制指令？ → A: 透過 MQTT 協議（設備與後端都連接至 MQTT Broker，透過 Pub/Sub 模式交換資料）
- Q: 系統應該採用何種等級的安全性措施來保護管理人員的帳號與通訊安全？ → A: 基本加密與密碼規則（HTTPS 加密通訊、密碼使用 bcrypt/Argon2 雜湊儲存、要求至少 8 字元含英數字）
- Q: 系統應該針對遠端控制指令實施何種頻率限制，以防止誤操作或過度頻繁的設備切換？ → A: 每台設備每 10 秒最多 1 次控制指令（同一設備 10 秒內重複指令會被拒絕並顯示提示）
- Q: 系統應該設定怎樣的可靠性與可用性目標？ → A: 高可靠性（目標 99% 可用性，每月停機時間不超過 7.2 小時，需實作備援機制）
- Q: 系統前端應該採用何種技術框架來實作網頁介面？ → A: React + TypeScript（主流框架，豐富生態系統，適合複雜互動與資料視覺化）

## 使用者情境與測試 *(必填)*

### 使用者故事 1 - 全域儀表板一覽設備狀態 (優先級: P1)

管理人員使用帳號密碼登入系統後，能在全域儀表板上一眼看到所有熱泵設備的總覽資訊，包括目前有多少台設備在線上、總共消耗了多少電力、產生了多少熱能，以及整體的運作效率（COP）。左側設備清單會列出所有熱泵站（如 A、B、C 站），並用紅、綠、灰燈號標示哪些設備在運作、停止或出現異常。右上角的通知圖示會顯示未讀通知數量，點擊後可查看異常事件歷史記錄。

**為何此優先級**：這是系統的核心價值所在。管理人員首先需要知道「大局」－有多少設備運作中、是否有異常狀況。這是遠端管理中心的最基本需求，沒有這個功能，系統就失去了「遠端掌握全局」的意義。

**獨立測試**：打開網頁後，立即能看到總覽數據（在線設備數、總耗電量、總產熱量、整體COP），以及左側設備清單顯示各站狀態燈號。這個功能可以單獨展示，即使其他詳細功能尚未完成，管理人員也能獲得「遠端總覽」的價值。

**驗收情境**：

1. **假設** 管理人員不在機房現場，**當** 他在公司辦公室打開網頁並使用帳號密碼登入，**則** 能看到網頁最上方顯示總覽資訊，包含「在線設備：5台」、「總耗電：120kW」、「總產熱：480kW」、「整體COP：4.0」
2. **假設** 系統目前連接了 A、B、C 三個熱泵站，**當** 管理人員查看左側設備清單，**則** 能看到三個站點名稱，A站顯示綠燈（運作中）、B站顯示綠燈（運作中）、C站顯示紅燈（異常，因為排氣溫度超過85°C閾值）
3. **假設** C站因為溫度異常而被標示為紅燈，**當** 管理人員看到紅燈，**則** 知道該站需要關注，可以進一步點選查看詳細狀況
4. **假設** 某台設備突然離線，**當** 系統偵測到設備離線，**則** 該設備燈號立即變為灰色，並在總覽資訊中更新「在線設備」數量，同時在通知中心產生一則「設備 X 已離線」的通知訊息
5. **假設** 管理人員離開儀表板一段時間後再次登入，**當** 在這段期間內發生了3次異常事件，**則** 右上角通知圖示顯示「3」的未讀數字，點擊後可看到這3則異常通知的詳細內容與發生時間

### 使用者故事 2 - 設備運作動態圖視覺化 (優先級: P2)

管理人員選擇某個設備後，能在網頁中央看到一張「動態流程圖」，視覺化呈現壓縮機、風扇、水箱等實體零件，並且當設備運轉時，畫面上會有動態效果（例如流向導引或顏色變化），讓使用者直覺看到熱水現在流到哪裡、溫度幾度。下方清單會列出每個零件（如：1號風扇、循環幫浦）是否正常轉動。

**為何此優先級**：視覺化動態圖讓管理人員能夠「直覺理解」設備運作狀態，不需要對照複雜的數字表格。這對於快速診斷問題、理解設備運作邏輯非常有幫助。這是「易用性」和「專業性」的平衡點。

**獨立測試**：點選某台設備後，能看到該設備的動態流程圖，顯示各元件圖示及其即時狀態（運轉中/停止），並在設備運轉時看到動態流向效果。這個功能可以獨立展示設備的「視覺化監控」能力。

**驗收情境**：

1. **假設** 管理人員想了解 A站的運作細節，**當** 點選左側清單中的 A站，**則** 網頁中央區域顯示 A站的動態流程圖，包含壓縮機、風扇、水箱、管路等元件圖示
2. **假設** A站正在運轉，**當** 管理人員觀看動態流程圖，**則** 能看到流體流向的動態效果（例如箭頭動畫或流動線條），以及各關鍵節點顯示即時溫度數值（入水溫度：15°C、出水溫度：55°C）
3. **假設** 管理人員想了解各零件狀態，**當** 向下捲動至零件清單區域，**則** 能看到「1號風扇：運轉中」、「2號風扇：運轉中」、「循環幫浦：運轉中」、「壓縮機：運轉中」的詳細狀態清單
4. **假設** 循環幫浦突然停止運轉，**當** 系統偵測到狀態變化，**則** 動態流程圖中該幫浦圖示變為灰色或停止動畫，且零件清單中顯示「循環幫浦：已停止」

### 使用者故事 3 - 即時趨勢圖表數據分析 (優先級: P3)

管理人員能在網頁上看到壓力、頻率與溫度等參數轉換為曲線圖，觀察過去幾分鐘到幾小時內的數據波動，判斷設備運作是否穩定。例如，如果發現排氣溫度異常飆高，系統會在圖表上以明顯顏色標示，讓管理人員第一時間察覺。

**為何此優先級**：趨勢圖表能幫助管理人員進行「預測性維護」－透過觀察數據波動趨勢，提前發現潛在問題。這對於長期設備管理很有價值，但在初期 MVP 階段，即時狀態監控的優先級更高。

**獨立測試**：在設備頁面下方或獨立區域，能看到壓力、頻率、溫度的即時曲線圖，可選擇時間範圍（過去10分鐘、1小時、6小時等），並能清楚看到數據波動情況。這個功能可以獨立展示「數據分析」能力。

**驗收情境**：

1. **假設** 管理人員想了解設備溫度變化，**當** 在設備頁面查看趨勢圖表區域，**則** 能看到「排氣溫度」、「吸氣溫度」、「水箱溫度」三條曲線圖，橫軸顯示時間，縱軸顯示溫度值
2. **假設** 管理人員想觀察較長時間的趨勢，**當** 點選時間範圍選項「過去6小時」，**則** 圖表更新為顯示過去6小時的數據曲線
3. **假設** 在過去30分鐘內，排氣溫度曾異常升高至95°C（超過85°C閾值），**當** 管理人員查看趨勢圖表，**則** 能在圖表上看到該時段的溫度峰值，並以紅色或警示顏色標示異常區段
4. **假設** 管理人員想同時觀察多個參數，**當** 在圖表上方勾選「壓力」、「頻率」、「溫度」複選框，**則** 三條不同顏色的曲線同時顯示在同一圖表上，方便對比分析

### 使用者故事 4 - 遠端遙控設備參數 (優先級: P4)

管理人員可以直接在網頁上將設備從「自動模式」切換為「手動模式」，並且如果發現水溫不夠，不需要去現場轉旋鈕，直接在網頁輸入目標溫度並送出，設備就會依照新指令運作。這是本專案的關鍵功能，打破了「必須到現場才能控制設備」的限制。設備控制區域會顯示最近5筆操作記錄（包含操作者名稱與操作時間），讓管理人員清楚知道設備最近的控制歷史。

**為何此優先級**：遠端控制是「遠端管理」的終極目標，能大幅減少管理人員的現場巡檢次數。但這個功能需要監控功能作為基礎－管理人員必須先看到設備狀態，才能做出正確的控制決策。因此優先級排在監控功能之後。

**獨立測試**：在設備控制區域，能看到「模式切換」按鈕（自動/手動）和「目標參數設定」輸入欄位（如目標水溫）。點選切換模式後，系統送出指令並顯示確認訊息。這個功能可以獨立展示「遠端控制」能力。

**驗收情境**：

1. **假設** 管理人員需要手動調整設備，**當** 在設備頁面的控制區域點選「切換至手動模式」按鈕，**則** 系統顯示確認對話框「確定要切換至手動模式嗎？」
2. **假設** 管理人員確認切換，**當** 點擊「確認」按鈕，**則** 系統送出指令至設備，並在畫面上顯示「指令傳送中...」載入提示
3. **假設** 設備成功接收指令，**當** 設備回應確認，**則** 系統在3秒內更新介面，顯示「目前模式：手動」，並啟用參數調整功能
4. **假設** 設備現在處於手動模式，**當** 管理人員在「目標水溫」欄位輸入「60」並點擊「套用」按鈕，**則** 系統送出新的溫度設定，設備開始調整運作以達到目標溫度
5. **假設** 管理人員在偏遠地區使用手機，網路訊號較弱，**當** 執行遠端控制操作，**則** 系統顯示「指令傳送中...」載入提示，即使網路較慢也不會讓畫面當機或變空白
6. **假設** 設備目前離線，**當** 管理人員嘗試遠端控制，**則** 系統顯示錯誤訊息「設備目前離線，無法執行遠端控制」，並停用控制按鈕
7. **假設** 管理人員想了解設備最近的控制歷史，**當** 查看設備控制區域下方的操作記錄清單，**則** 能看到最近5筆操作，包含「2026-02-19 14:30 - 張經理：切換至手動模式」、「2026-02-19 14:32 - 張經理：設定目標水溫 60°C」等資訊

### 使用者故事 5 - 跨裝置響應式操作 (優先級: P5)

管理人員無論使用桌上型電腦、筆記型電腦、平板或手機，介面都會自動調整版面配置，確保資訊清晰可讀且操作方便。這確保了管理人員可以在任何地點、使用任何裝置進行遠端管理。

**為何此優先級**：響應式設計是使用者體驗的重要一環，確保「隨時隨地」的遠端管理能力。但在功能開發初期，可以先在桌面版本上驗證核心功能，再優化行動裝置體驗。因此優先級相對較低。

**獨立測試**：使用不同尺寸的裝置（桌機、平板、手機）開啟網頁，驗證介面元素是否適當調整大小和位置，按鈕和輸入欄位是否易於點擊和操作。這個功能可以獨立展示「跨裝置相容性」。

**驗收情境**：

1. **假設** 管理人員使用桌上型電腦（螢幕解析度 1920x1080），**當** 開啟儀表板，**則** 設備清單顯示在左側固定欄位，中央顯示動態流程圖，右側或下方顯示趨勢圖表，版面配置橫向展開
2. **假設** 管理人員使用平板電腦（螢幕解析度 768x1024），**當** 開啟儀表板，**則** 設備清單收合為可展開的選單或下拉選項，流程圖和圖表垂直排列，確保內容清晰可讀
3. **假設** 管理人員使用手機（螢幕解析度 375x667），**當** 開啟儀表板，**則** 所有元素垂直堆疊，設備清單位於頂部下拉選單，流程圖和圖表佔滿螢幕寬度，確保在小螢幕上也能清楚看到資訊
4. **假設** 管理人員使用手機點擊控制按鈕，**當** 手指觸碰按鈕，**則** 按鈕大小足夠（至少 44x44 像素），且點擊後有明確的視覺回饋（顏色變化或動畫效果）
5. **假設** 管理人員在手機上查看趨勢圖表，**當** 向下滑動頁面，**則** 圖表能順暢捲動，且可用雙指縮放查看細節

### 邊界情境

- **登入失敗處理**：當管理人員輸入錯誤的帳號或密碼時，系統應顯示「帳號或密碼錯誤」的明確訊息。連續失敗3次後，該帳號暫時鎖定5分鐘。鎖定期間任何登入嘗試直接回傳「帳號已鎖定，請在 X 分鐘後再試」（X 為剩餘分鐘數），不驗證密碼。5 分鐘後自動解鎖，失敗計數器重置。初期版本無「忘記密碼」功能，若使用者真正遺忘密碼，需聯絡系統管理員透過資料庫操作重設（重設步驟詳見 quickstart.md 的管理員操作指南章節）
- **Session過期處理**：當管理人員登入後超過8小時未操作，系統應自動登出並顯示「登入已過期，請重新登入」訊息。若管理人員在 Session 過期狀態下嘗試操作，系統應重新導向至登入頁面
- **閾值邊界值處理**：當參數值剛好等於閾值（例如排氣溫度正好85°C）時，系統判定為正常，不觸發異常。只有超過（>）閾值時才判定為異常。這避免了在邊界值附近頻繁切換狀態的問題
- **多參數同時異常**：當一台設備同時出現多個參數異常（例如排氣溫度和壓力都超過閾值）時，系統應產生一則綜合通知，列出所有異常參數，而非產生多則重複通知
- **網路收訊不好時**：當管理人員的網路不穩定，系統應顯示「讀取中...」或明確的提示訊息，不會讓畫面直接當機或變空白。如果資料載入超過5秒，應顯示「網路連線異常，正在重試...」
- **設備突然離線**：當設備因為停電或網路中斷而突然離線，系統應在30秒內偵測到並更新設備狀態為「離線」，燈號變為灰色，且遠端控制功能自動停用。為避免網路抖動造成燈號頻繁切換，實作防抖（debounce）邏輯：設備需持續 30 秒無資料才標記為 OFFLINE；設備恢復後需連續接收 2 次資料（約 1 分鐘）才標記為 ONLINE
- **資料更新延遲**：如果超過30秒未收到新的設備資料，系統應在畫面上顯示「資料可能已過時」的警告訊息，避免管理人員誤判
- **多人同時操作同一設備**：當兩位管理人員同時嘗試控制同一設備時，系統採用「最後指令優先」策略，後送出的指令會覆蓋先前的指令。系統必須記錄所有操作紀錄（包含操作者帳號、操作者顯示名稱、操作時間、操作內容），並在設備控制區域顯示最近5筆操作記錄，讓管理人員可以追蹤誰執行了哪些操作
- **操作記錄保存期限**：系統保存所有遠端控制操作記錄至少30天（與即時資料保存期限一致），超過30天的操作記錄隨資料清理作業一併刪除
- **異常資料值處理**：當設備回傳明顯錯誤的資料（例如溫度 -999°C 或壓力 999 MPa），系統應標示為「資料異常」，不顯示在趨勢圖上，避免干擾判讀
- **大量設備同時連線**：系統設計為支援最多 50 台設備同時連線。在此規模下，可採用全部載入策略，無需複雜的分頁或虛擬滾動技術。當設備數量接近上限時，系統應確保儀表板載入時間仍維持在 5 秒以內
- **通知訊息過多處理**：當未讀通知數量超過99則時，通知圖示顯示「99+」。通知中心面板一次最多顯示最近50則通知，較舊的通知可透過「載入更多」按鈕查看。超過 30 天的通知隨每日資料清理作業一併刪除，與遙測資料保存策略一致
- **歷史資料查詢邊界**：當管理人員嘗試查詢超過30天前的歷史資料時，系統顯示「僅保存最近30天的資料」提示訊息，並自動調整查詢範圍至最早可查詢日期
- **資料清理執行中**：系統在執行每日資料清理作業時（刪除超過30天的舊資料），不影響前端即時監控與資料查詢功能。清理作業設計為背景批次處理，不鎖定正在使用的資料表
- **控制指令速率限制**：為保護設備免於頻繁切換造成損壞，系統對每台設備實施 10 秒的控制指令冷卻期。當管理人員對同一台設備送出控制指令後，該設備在 10 秒內無法接受新的控制指令（無論來自同一或不同管理人員）。若管理人員在冷卻期內嘗試送出新指令，系統顯示明確提示訊息「此設備剛完成操作，請等待 X 秒後再試」（X 為剩餘秒數）。不同設備之間的控制指令互不影響，管理人員可以同時對多台不同設備下達指令

  - 控制指令操作記錄（ControlCommand）

- **即時通訊**：WebSocket + Socket.io（用於接收後端推送的即時設備資料與通知，支援房間管理與自動重連）
- **HTTP 客戶端**：Axios 或 Fetch API（處理 RESTful API 請求）
- **路由管理**：React Router v6+（處理多頁面導航）
- **樣式方案**：CSS Modules 或 Styled Components（模組化樣式，避免命名衝突）
- **建置工具**：Vite 或 Create React App（快速開發環境與生產建置）

**前端架構設計原則**：
- **元件化設計**：將 UI 拆解為可重用元件（如 DeviceCard、TrendChart、ControlPanel），提高開發效率與維護性
- **響應式布局**：使用 Flexbox 或 CSS Grid 實作，搭配媒體查詢（Media Queries）適配不同螢幕尺寸
- **效能最佳化**：
  - 使用 React.memo 避免不必要的元件重新渲染
  - 圖表資料採用虛擬化或分頁載入，避免一次渲染過多資料點
  - 靜態資源（圖片、字型）使用延遲載入（Lazy Loading）
  - 路由層級的程式碼分割（Code Splitting），減少首次載入時間
- **無障礙設計**：遵循 WCAG 2.1 AA 標準，確保鍵盤導航、螢幕閱讀器相容性

**設備通訊協議**：系統採用 MQTT（Message Queuing Telemetry Transport）協議作為後端與實體熱泵設備之間的通訊機制。MQTT 是專為物聯網（IoT）環境設計的輕量級訊息協議，特別適合低頻寬、不穩定網路環境，並支援雙向即時通訊。

**架構組成**：
- **MQTT Broker**：作為中央訊息代理（Message Broker），負責接收、路由、分發所有訊息。可使用成熟的開源實作如 Mosquitto 或 EMQX
- **熱泵設備（MQTT Client）**：每台熱泵設備作為 MQTT Client，定期發布（Publish）即時監測資料到指定的 Topic（例如 `devices/{device_id}/telemetry`），並訂閱（Subscribe）控制指令 Topic（例如 `devices/{device_id}/commands`）
- **後端服務（MQTT Client）**：後端服務同樣作為 MQTT Client，訂閱所有設備的遙測資料 Topic（例如 `devices/+/telemetry`），並在需要執行控制指令時，發布訊息到特定設備的控制 Topic

**資料流向**：
- **監測資料流（設備 → 後端）**：設備每 30 秒發布一次完整的監測資料（JSON 格式），包含所有感測器數值、零件狀態、運作模式等資訊，發布到 `devices/{device_id}/telemetry` Topic。後端訂閱此 Topic，接收資料後儲存至資料庫，並透過 WebSocket 或 Server-Sent Events 推送至前端介面
- **控制指令流（後端 → 設備）**：當管理人員執行遠端控制操作時，後端發布控制指令（JSON 格式）到 `devices/{device_id}/commands` Topic。設備接收指令後執行動作，並在 3 秒內發布確認訊息到 `devices/{device_id}/command-ack` Topic，讓後端更新指令執行狀態
- **設備狀態偵測**：後端透過 MQTT 的 Last Will and Testament（LWT）機制偵測設備離線。當設備連線時設定 LWT 訊息到 `devices/{device_id}/status` Topic，內容為 `{"status": "offline"}`。若設備意外斷線，Broker 會自動發布此訊息，後端收到後立即更新設備狀態為離線

**訊息格式範例**：
- 遙測資料：`{"timestamp": "2026-02-19T14:30:00Z", "mode": "auto", "temperatures": {"exhaust": 82.5, "suction": 15.3, "water_in": 15.0, "water_out": 55.2}, "pressures": {"high": 3.2, "low": 0.5}, "components": {"compressor": "running", "fan1": "running", "fan2": "running", "pump": "running"}, "power": {"consumption_kw": 24.5, "heat_output_kw": 98.0, "cop": 4.0}}`
- 控制指令：`{"command_id": "cmd_12345", "type": "set_mode", "value": "manual"}` 或 `{"command_id": "cmd_12346", "type": "set_target_temp", "value": 60}`
- 指令確認：`{"command_id": "cmd_12345", "status": "acknowledged", "timestamp": "2026-02-19T14:30:03Z"}`

**連線品質保證**：
- 使用 MQTT QoS 1（At Least Once）確保重要訊息（控制指令、異常事件）至少送達一次
- 使用 MQTT QoS 0（At Most Once）處理高頻遙測資料，減少網路負載
- 設備端實作自動重連機制，當網路中斷恢復後自動重新連接至 Broker
- 後端實作訊息緩衝機制，當設備離線時暫存控制指令，待設備重新上線後再次傳送

### 安全性與隱私

本系統設計為企業內部使用，採用基本但有效的安全措施，在易用性與安全性之間取得平衡。

**通訊加密**：
- 所有前端與後端之間的 HTTP 通訊必須使用 HTTPS（TLS 1.2 或更高版本）加密，防止中間人攻擊與資料竊聽
- WebSocket 或 Server-Sent Events 連線同樣必須使用加密協議（WSS 或 HTTPS）
- MQTT Broker 與 Client 之間的連線建議使用 MQTT over TLS（MQTTS），但考慮到企業內網環境的信任度，可在初期版本使用未加密 MQTT，後續版本升級為 MQTTS

**密碼儲存與驗證**：
- 使用者密碼必須使用業界標準的單向雜湊演算法（bcrypt 或 Argon2）儲存，嚴禁明文或可逆加密儲存
- 雜湊時必須加入隨機 Salt，確保相同密碼產生不同的雜湊值
- 密碼複雜度要求：至少 8 個字元，必須包含英文字母與數字
- 系統不強制要求特殊符號或大小寫混合，以降低使用者記憶負擔（考慮企業內部使用情境）
- **「簡化驗證」定義**：本系統採用的「簡化」帳號密碼驗證（如釐清事項所述），意指降低密碼複雜度要求（不強制特殊符號與大小寫混合），但仍維持基本的安全措施（密碼長度、雜湊儲存、失敗鎖定機制），適合企業內部低風險環境使用

**帳號保護機制**：
- 連續登入失敗 3 次後，該帳號自動鎖定 5 分鐘，防止暴力破解攻擊
- 鎖定期間內的登入嘗試不計入失敗次數，避免攻擊者無限延長鎖定時間
- 成功登入後重置失敗次數計數器
- 不提供「密碼提示」功能，避免洩漏密碼相關資訊

**Session 管理**：
- 使用者成功登入後，系統產生唯一的 Session Token（建議使用 UUID v4 或安全隨機字串）
- Session Token 儲存於後端資料庫或快取系統（如 Redis），並設定 8 小時有效期限
- 前端將 Session Token 儲存於 HttpOnly Cookie 中，防止 JavaScript 存取（降低 XSS 攻擊風險）
- Session 過期後自動登出，使用者需重新登入
- 提供明確的「登出」功能，立即失效當前 Session Token

**輸入驗證與防護**：
- 所有使用者輸入（帳號、密碼、控制參數）必須在前端與後端雙重驗證格式與範圍
- 防止 SQL Injection：使用參數化查詢（Prepared Statements）或 ORM 框架
- 防止 XSS 攻擊：輸出至網頁的所有使用者產生內容必須進行 HTML 跳脫處理
- 控制參數驗證：目標溫度、壓力等數值必須在合理範圍內（例如水溫 0-100°C），超出範圍直接拒絕

**存取控制**：
- 所有需要登入才能存取的 API 端點，必須驗證 Session Token 有效性
- 未登入或 Session 過期的請求，自動回傳 HTTP 401 Unauthorized 狀態碼
- 前端偵測到 401 回應時，自動重新導向至登入頁面

**隱私保護**：
- 系統不記錄使用者密碼的明文或可還原形式
- 操作記錄中僅儲存「操作者顯示名稱」（如「張經理」），不記錄敏感個人資訊
- 30 天後自動清理的歷史資料包含操作記錄，確保資料不無限期保留

**未來擴展建議**（初期版本可不實作）：
- 若未來擴展至公網存取或多組織使用，建議升級至 JWT Token 機制、實作角色權限控制（RBAC）、整合企業 LDAP/AD 身份認證
- 若安全需求提升，可考慮加入多因素認證（MFA）、IP 白名單限制、完整稽核日誌等功能

### 可靠性與可用性

**可用性目標**：系統設定為高可靠性等級，目標可用性為 **99%**（Two Nines），意即在任何連續 30 天週期內，系統停機時間不超過 **7.2 小時**（含計劃性維護與非計劃性故障）。

**可用性計算基準**：
- 監控範圍：前端網頁介面可正常載入、後端 API 能正常回應、設備資料能正常更新
- 計入停機：HTTP 5xx 錯誤、連線逾時、資料庫無法存取、MQTT Broker 離線、前端白畫面或無法載入
- 不計入停機：用戶端網路問題、設備端離線（非系統問題）、瀏覽器相容性問題、用戶操作錯誤

**備援與容錯機制**：
- **資料庫備份**：每日自動執行完整資料庫備份，保留最近 7 天備份檔案於異地儲存。備份檔案必須能在 1 小時內完成還原
- **服務健康檢查**：後端服務必須提供健康檢查端點（Health Check Endpoint），每 30 秒由監控系統檢查一次。若連續 3 次檢查失敗（90 秒內），觸發告警通知維運人員
- **MQTT Broker 備援**：建議配置 MQTT Broker 主備架構（Primary-Standby）或叢集模式（Cluster），當主節點故障時，設備與後端能自動切換至備用節點，切換時間不超過 60 秒
- **資料庫連線池管理**：後端實作資料庫連線池機制，當資料庫短暫無法連線時，自動重試機制（最多重試 3 次，每次間隔 5 秒），避免單一查詢失敗導致整個服務崩潰
- **前端降級顯示**：當後端 API 暫時無法回應時，前端顯示最後一次成功獲取的資料（標註「資料可能已過時」），而非完全空白或錯誤畫面

**故障恢復能力**：
- **服務重啟時間**：後端服務（含資料庫、MQTT Broker、應用伺服器）必須能在 10 分鐘內完成重啟並恢復正常運作
- **資料一致性**：系統故障重啟後，必須確保資料完整性，不遺失最近 30 秒內的設備資料（MQTT QoS 1 保證）、不遺失任何控制指令記錄
- **Session 持久化**：用戶 Session 資料建議儲存於持久化快取系統（如 Redis with persistence），避免服務重啟後所有用戶被強制登出

**監控與告警**：
- **即時監控指標**：系統必須記錄關鍵效能指標（KPI），包含 API 回應時間、資料庫查詢時間、MQTT 訊息延遲、前端載入時間、錯誤率（4xx/5xx）
- **告警通知機制**：當偵測到以下異常狀況時，系統應透過電子郵件或即時通訊工具（如 Slack、Teams）通知維運人員：
  - 服務健康檢查連續失敗 3 次
  - API 錯誤率超過 5%（在 5 分鐘內）
  - 資料庫連線池耗盡或查詢時間超過 3 秒
  - MQTT Broker 離線或訊息堆積超過 1000 則
  - 磁碟空間使用率超過 85%
  - 記憶體使用率超過 90%

**計劃性維護**：
- 系統維護作業（版本更新、資料庫維護、伺服器重啟）應安排在低使用量時段（建議為週末凌晨 2:00-6:00）
- 重大維護作業應提前至少 3 個工作日通知所有管理人員，並在系統登入頁面顯示維護公告
- 計劃性維護時間應計入每月 7.2 小時的停機時間額度內

**災難復原計畫**：
- 制定災難復原程序文件（Disaster Recovery Procedure），記錄服務完全故障時的復原步驟、負責人員、聯絡方式
- 每季度至少執行一次災難復原演練（DR Drill），驗證備份還原流程與服務重建時間
- 目標復原時間（RTO, Recovery Time Objective）：4 小時（從故障發生到服務完全恢復）
- 目標復原點（RPO, Recovery Point Objective）：1 小時（最多可接受遺失 1 小時內的非關鍵資料，但控制指令記錄不可遺失）
